```
                       ▼

              │   SQLite DB      │
              │  (ファイルベース)   │
              └─────────────────┘
```

### 1.2 技術選定

| レイヤー | 技術 | 選定理由 |
|---------|------|---------|
| Bot フレームワーク | discord.py (Python) | 日本語情報が豊富、ボタン/スレッド対応済み |
| データベース | SQLite | 初期10人規模では十分、セットアップ不要、バックアップはファイルコピーで完結 |
| 画像認識 | Tesseract OCR + OpenCV | 雀魂の結果画面はレイアウト固定のためテンプレートマッチング+OCR が有効 |
| スケジューラ | APScheduler | Python 内蔵でcron的な定時実行が可能 |
| ホスティング | Oracle Cloud Always Free (ARM) | 永久無料枠、24時間稼働、Bot用途に十分な性能 |

### 1.3 将来の拡張パス
- SQLite → PostgreSQL（100人超で検討）
- OCR → Vision API / LLM（認識精度向上が必要な場合）

## 2. Discord チャンネル設計

### 2.1 固定チャンネル

| チャンネル名 | 種類 | 用途 |
|------------|------|------|
| `#麻雀マッチング` | テキスト | 参加受付ボタン・待機人数表示 |

## 3. UI設計（Discord メッセージ）

### 3.1 参加募集メッセージ (F-01, F-02)

```
━━━━━━━━━━━━━━━━━━━━━━
🀄 本日の麻雀部 開催中！
━━━━━━━━━━━━━━━━━━━━━━

【待機状況】
  4人戦：2人 待機中
  3人戦：1人 待機中

  [4人戦に参加]  [3人戦に参加]  [両方に参加]  [参加取消]
```

- 「両方に参加」= 3人戦・4人戦の同時エントリー（4人戦優先）
- ボタン押下時、ephemeral メッセージ（本人のみ表示）で確認を返す
- 待機人数はボタン操作のたびにメッセージを編集して更新

### 3.2 マッチング成立通知 (F-03, F-04)

```

ボイス：🔊 対戦卓-042

部屋番号を共有してゲームを開始してください。

  [辞退する]  [グループ解散]
```

### 3.3 辞退・補充通知 (F-05)

```

```

## 4. データベース設計

### 4.1 ER図

```
members ─────────< match_players >───────── matches
                                              │
                                              │
                                        match_results
```

### 4.2 テーブル定義

#### `members` — メンバー情報

| カラム名 | 型 | 制約 | 説明 |
|---------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 内部ID |
| discord_id | TEXT | UNIQUE, NOT NULL | Discord ユーザーID |
| display_name | TEXT | NOT NULL | 表示名（キャッシュ） |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 登録日時 |

#### `matches` — 対戦情報

| カラム名 | 型 | 制約 | 説明 |
|---------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 対戦ID |
| match_type | INTEGER | NOT NULL | 対戦種別（3 or 4） |
| status | TEXT | NOT NULL, DEFAULT 'waiting' | 状態（waiting / playing / finished / disbanded） |
| thread_id | TEXT | | 対戦スレッドID |
| voice_channel_id | TEXT | | ボイスチャンネルID |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 作成日時 |
| finished_at | DATETIME | | 終了日時 |

#### `match_players` — 対戦参加者（中間テーブル）

| カラム名 | 型 | 制約 | 説明 |
|---------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | ID |
| match_id | INTEGER | FK → matches.id, NOT NULL | 対戦ID |
| member_id | INTEGER | FK → members.id, NOT NULL | メンバーID |
| joined_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 参加日時 |

- UNIQUE制約: (match_id, member_id)

#### `match_results` — 対戦結果

| カラム名 | 型 | 制約 | 説明 |
|---------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | ID |
| match_id | INTEGER | FK → matches.id, NOT NULL | 対戦ID |
| member_id | INTEGER | FK → members.id, NOT NULL | メンバーID |
| rank | INTEGER | NOT NULL | 順位（1〜4） |
| score | INTEGER | NOT NULL | 素点（例: 45000） |
| point | REAL | NOT NULL | ポイント（ウマ込み、例: +45.0） |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 記録日時 |

- UNIQUE制約: (match_id, member_id)

### 4.3 インデックス

| テーブル | カラム | 用途 |
|---------|--------|------|
| members | discord_id | ユーザー検索 |
| matches | status | アクティブ対戦の検索 |
| matches | created_at | 期間指定クエリ |
| match_results | member_id | メンバー別成績集計 |
| match_results | (member_id, created_at) | 期間別ランキング |

## 5. Botコマンド設計

### 5.1 スラッシュコマンド一覧

| コマンド | 引数 | 権限 | 説明 | 対応機能 |
|---------|------|------|------|---------|
| `/result` | @user1 rank1 score1 ... | 全員 | 対戦結果を手動入力 | F-06 |
| `/ranking` | [期間: 月間/通算] | 全員 | ランキング表示 | F-08 |

### 5.2 ボタンインタラクション一覧

| ボタンID | ラベル | 動作 |

## 6. 処理フロー設計

### 6.1 マッチングフロー

```
[定時 0:00] スケジューラ起動
    │
    ▼
Bot が #麻雀マッチング に募集メッセージを投稿
    │
    ▼
┌─── ユーザーがボタン押下 ◄──────────────────────┐
│       │                                       │
│       ▼                                       │
│   待機キューに追加                               │
│   (queue_4 / queue_3 / 両方)                   │
│       │                                       │
│       ▼                                       │
│   待機人数を更新表示                              │
│       │                                       │
│       ▼                                       │
│   ┌─ 4人戦キュー >= 4人？ ─── Yes ──┐           │
│   │       │                       │           │
│   │      No                       ▼           │
│   │       │              ランダムに4人抽出       │
│   │       ▼              (両方エントリー者優先)    │
│   │  3人戦キュー >= 3人？         │              │
│   │       │              ▼              │
│   │      No ── 待機継続 ──►  マッチング成立       │
│   │       │                    │              │
│   │      Yes                   ▼              │
│   │       │           スレッド＋VC作成           │
│   │       ▼           メンバーに通知             │
│   │  ランダムに3人抽出     抽出者をキューから除去    │
│   │       │                    │              │
│   │       ▼                    │              │
│   │  マッチング成立              │              │
│   │       │                    │              │
│   └───────┴────────────────────┘              │
│                                               │
└───────── キュー残りで再チェック ─────────────────┘
```

### 6.2 辞退・補充フロー

```
[辞退ボタン押下 or /disband]
    │
    ▼
辞退者をグループから除去
    │
    ▼
┌─ 待機キューに同種別の待機者がいるか？
│       │
│      Yes ──► ランダムに1人を補充
│       │        │
│       │        ▼
│       │     補充通知を送信
│       │     グループ継続
│       │
│      No ──► グループ解散
│               │
│               ▼
│            残メンバーに解散通知
│            スレッドをアーカイブ
│            VCを削除
│            残メンバーを待機キューに戻す（希望者のみ）
└────────────────────────────────────────
```

### 6.3 成績記録フロー

```
[ユーザーが #対戦結果 にスクリーンショットを送信]
    │
    ▼
Bot が画像を受信
    │
    ▼
OpenCV で雀魂結果画面を検出
    │
    ▼
┌─ 結果画面として認識できたか？
│       │
│      Yes ──► Tesseract OCR で順位・スコアを抽出
│       │        │
│       │        ▼
│       │     認識結果を表示 + [確定] [修正する] ボタン
│       │        │
│       │        ├── [確定] ──► DB に保存
│       │        │
│       │        └── [修正する] ──► 手動入力フローへ
│       │
│      No ──► 「認識失敗」メッセージ
│               │
│               ▼
│            /result コマンドでの手動入力を案内
│               │
│               ▼
│            DB に保存
└────────────────────────────────────────
```

## 9. 設計上の判断と根拠

| 判断 | 根拠 |
|------|------|
| SQLite を採用 | 初期10人・将来100人規模では十分な性能。サーバー不要でバックアップも容易。PostgreSQLへの移行パスも確保 |
| 待機キューはメモリ管理 | Bot再起動時にキューがリセットされても運用上問題なし（毎日0時開催のため）。DBに永続化する複雑さを回避 |
| 対戦グループはスレッドで管理 | チャンネル増殖を防ぎつつ、グループごとの会話を分離できる。アーカイブで履歴も残る |
| ボイスチャンネルは動的生成 | 常設すると使わない時にチャンネルリストが煩雑になる。マッチング成立〜解散のライフサイクルで自動管理 |
| 画像認識は Tesseract + OpenCV | 雀魂の結果画面はレイアウトが固定されているため、領域指定+OCRで十分な精度が見込める。API課金なし |
